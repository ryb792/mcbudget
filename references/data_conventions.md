# McBudget 数据约定（演示 / 真实共享）

目的：保证演示模式与真实模式对"金额、候选、排序、状态"的计算含义完全一致。`scripts/budget_engine.py` 与 `scripts/engine.js`（演示页内嵌）是同一算法的两种实现，`scripts/test_engine_parity.py` 验证两者输出字节级一致。

## 1. 就餐方式（先于选餐确认）

`order_type` 三值：`pickup`（到店取餐，beType=1，含堂食/自取子项——由算价 takeWayList 决定）、`dt`（得来速，beType=5）、`delivery`（麦乐送，beType=2）。**菜单、价格、券与门店随方式变化**：方式未确认不查菜单、不建候选、不算价；方式互切时菜单/券/门店上下文全部重查重算，禁止沿用旧候选。pickup 与 dt 均无配送费；delivery 配送费以算价为准（估算阶段用预设下限）。

## 2. 金额

- 内部表示：整数"分"（int cents）。展示层 ÷100。
- 外部输入按来源显式声明单位：`user_yuan`（用户预算，元）、`menu_yuan`（菜单，元字符串）、`quote_cents`（算价，整数分）、`order_yuan`（订单，元字符串）。
- 转换只经 `to_cents / from_cents`；四舍五入仅在元→分时 HALF_UP 到分。
- 一致性恒等式：`应付 = 商品金额 − 优惠 + 配送费`。任何报价（含官方）不满足即视为解析错误，不得继续使用。

## 3. 上下文契约（ctx）

```json
{
  "budget_cents": 2500,            // 应付总额上限（含配送费）
  "order_type": "pickup",          // pickup 到店取餐 | dt 得来速 | delivery 麦乐送（先于选餐确认，决定菜单上下文）
  "menu": [                        // 统一菜单（已适配为分）
    {"code": "1002", "name": "麦辣鸡腿堡", "category": "main|combo|snack|drink|other",
     "price_cents": 1650, "tags": ["鸡肉"], "combo_items": [{"name": "中薯条"}]}
  ],
  "sample": null,                  // 演示样例（demo 模式必填，real 模式为 null）
  "prefs": ["鸡肉"],               // 口味偏好关键词
  "excluded": ["咖啡"],            // 排除项关键词（命中名称或 tags 即排除）
  "must": ["麦辣"]                 // 必选餐品关键词（购物车须含匹配项，含套餐组成）
}
```

## 4. 候选生成（确定性）

- 组合规则：恰好 1 份主餐（main 或 combo）；套餐即完整购物车（V1 不猜子项）；非套餐可搭配 0~1 小食、0~1 饮品；单品不重复，不为花光预算堆叠。
- 过滤：排除项命中任何成员即弃置；必选关键词无法满足即弃置。
- 去重：购物车签名 = 排序后 `(code, qty)` 串（如 `1002x1;4001x1`），同签名仅保留首个。
- 上限：每轮 ≤30 个候选；按 `（偏好命中数 降, 签名 升）` 排序后截断。

## 5. 定价与排序（性价比导向，套餐优先；2026-10-10 更新）

- **领券前置**：真实模式在构建候选前先 `auto-bind-coupons`（用户明确拒绝时跳过），再查门店可用券进入算价；演示模式样例券直接参与定价。券的实际减免以算价结果为准。
- 演示模式：`demo_price_cart` 按样例券规则取**最优单券**（item/order/category 三类；同一券只减一次），外送按样例规则（满 39 免 9 元配送费）。
- 真实模式：先按菜单价+固定配送费**估算**（排序与安排核价顺序），再对排序后前 ≤12 个去重购物车调 `calculate-price`；成功 → priced，失败/超时 → quote_failed。估算价不作为预算判定依据。
- **偏好命中（仅主餐口径）**：main/combo 的名称+tags+**套餐组成**参与关键词匹配（真实菜单无 tags 时组成名也能命中"鸡肉"类偏好）；小食/饮品的命中不计入偏好，只计入覆盖度。
- **覆盖度（coverage）**：主餐 1 + 套餐组成计件（通常 3）+ 单点小食/饮品各 1 + 用户槽位命中各 1。套餐天然覆盖更高。
- **代表方案排序键**：`（偏好命中 ↓ → 套餐组优先 ↓ → 覆盖度 ↓ → 实付 ↑ → 签名 ↑）`。同偏好下套餐组整体先于非套餐组——预算内优先推荐套餐（性价比），套餐不可行时回落覆盖最高的单点组合；"不堆叠重复餐品"仍由候选枚举（0-1 小食/饮品）保证。
- 三档（B-5/B/B+5）共享同一批候选与报价。

## 6. 状态机

| 状态 | 含义 | 展示要求 |
|------|------|----------|
| demo_sample | 演示样例定价 | 永久标记"演示样例价格" |
| estimated | 待核价（真实模式估算） | 标注"以官方算价为准" |
| priced | 已核价（官方 calculate-price） | 可作为确认下单依据 |
| quote_failed | 核价失败 | 不得展示为可行方案 |
| carry_over | 高档沿用低档同一方案 | 说明"暂时没有符合偏好的升级" |
| unsolvable | 本档无可行方案 | 给出已核候选最低金额与差额，不编造低价套餐 |

## 7. 增减解释

相邻档位代表方案 diff（按 code 集合）：增加/去掉/替换/数量变化 + 金额归因（商品/优惠/配送费分项），并声明"差额来自实际餐品与报价，不是预算档位差额"。文案模板见引擎 `explain_delta`，两实现一致。

## 8. 隐私红线（分享卡与日志）

不得输出：Token、手机号、具体地址、券码（couponCode）、支付链接（payH5Url）、完整订单号（orderId 展示时可尾 4 位截断并注明）。挑战卡只含：预算、餐品、应付、剩余、升级变化、报价时间、数据状态。
